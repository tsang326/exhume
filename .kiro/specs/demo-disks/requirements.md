# Requirements Document

## Introduction

This spec delivers the demo floppy disks of Exhume: three small FAT12 images that a judge or visitor opens with one click on the web page, and that the MCP server and Crew app can use as sample input. The images are produced by a deterministic generator script, `scripts/make-demo-disks.ts`, and committed in `public/disks/`. Every byte of file content is authored by this project. The README and the disks themselves say that the images are generated.

The three disks, from "Spec 5 — demo disks" in `docs/SPEC_BRIEFS.md`:

1. **Writer's disk**: WordStar chapters, one deleted draft that grades `recovered`, one deleted draft that grades `partial`.
2. **Small-business disk**: a dBase III customer table, a PCX logo, and one deleted file that grades `lost`.
3. **Damaged disk**: a bad BPB and a cyclic cluster chain, so that the reader reports warnings.

The `lost` file on the small-business disk is an addition to the brief. Without it, no demo disk shows all three undelete grades (`recovered`, `partial`, `lost`), which are the honest grading that `product.md` names as a new part of Exhume.

The generator reuses finished modules and changes none of them. It adds only new files: the demo-disk modules, the script, the tests, and one new pure helper `src/test-support/demo-source-scan.ts` (the source scanner of Requirement 1, criterion 6) with its test:

- `src/test-support/fat12/index.ts`: `writeFat12Image`, `FileTree`, `FileNode`, `DirNode`, `DamageSpec`, `StandardGeometryName`. The module has no test-runner, Node or `src/core` import, and its design says `scripts/make-demo-disks.ts` can call it directly.
- `src/test-support/formats/index.ts`: `writeWordStar`, `writeDbf`, `encodePcx` (and `parseCsv`, `decodePng` for tests). These are the fixture writers of the format-resurrection spec.
- For verification only, the existing reader and converters: `openDisk` and `DiskHandle` from `src/core/fat12/index.ts`, `convertAuto` from `src/core/formats/index.ts`.

The web side already has a slot for these disks. `src/web/demos.ts` holds an empty `DEMO_REGISTRY` documented as the extension point for this spec, and `validateDemoDisk` accepts only entries whose URL starts with `/disks/`. This spec fills the registry and does not change how `demos.ts` loads a file. Two existing web tests assume an empty registry (`src/web/demos.test.ts` and `src/web/dom/demo-slot.dom.test.ts`); this spec makes exactly one minimal edit to each (Requirement 9, criteria 5 and 6).

The Reader shows a deleted directory entry with its first character replaced by `_`, so the deleted files appear under Reader_Paths `/_RAFT1.WS`, `/_RAFT2.WS` and `/_LDCUST.DBF`. The names `DRAFT1.WS`, `DRAFT2.WS` and `OLDCUST.DBF` remain the names the Generator gives to the Image_Writer. Requirements that describe what the Reader or the Converter sees use the Reader_Paths.

A disk image is untrusted bytes by the project's safety rules, and the demo disks are no exception for the reader. They are, however, authored by us, so the generator itself is held to a stricter standard than the reader: byte-for-byte determinism, no network, no clock, no randomness, no secrets, no executable content.

### Decisions already made by the user

1. Two to three images in `public/disks/`; this spec produces three.
2. The generator is `scripts/make-demo-disks.ts`, deterministic, reusing the test-only FAT12 writer and fixture writers.
3. Expected outcomes are checked with the existing reader, grader and converters.
4. The README states that the images are generated by our script.
5. The agent does not run `npm run make:demos` (with or without `--check`) and does not write, create or modify anything in `public/disks/`. The user runs the generator the first time, after reviewing the generator code, and commits the images. The agent verifies the disk contents only through Fresh_Images held in memory.

### Out of scope

Any change to an existing file under `src/core/`; any change to an existing file under `src/test-support/` (a missing writer feature is reported to the user, not patched here; only the new files `src/test-support/demo-source-scan.ts` and its test may be added there); any change to how `src/web/demos.ts` fetches or validates (only the content of `DEMO_REGISTRY` and its comment change); any web test or web source change other than the two minimal test edits of Requirement 9, criteria 5 and 6; any `tsconfig.json` change other than adding `"scripts"` to `include`; the web UI, the MCP server and the Crew app; hosting configuration; hooks; running `npm run make:demos` by the agent; any write by the agent to `public/disks/`; adding or changing a dependency; real historical software, documents or fonts; a `.gitignore` change.

### Open points for the design phase (not decided here)

- How the TypeScript script runs. The imports in `src/` are extensionless, so plain `node scripts/make-demo-disks.ts` cannot resolve them. Requirement 2 fixes the observable behavior (an npm script, no new dependency); the design chooses the mechanism, for example the Vite-based approach that `build:mcp` already uses.
- Where tests for the generator live. `vitest.config.ts` includes only `src/**/*.test.ts`, so either the testable content and build functions sit under `src/` or the include list changes. The design decides; Requirement 10 only requires that `npm test` runs them.
- The exact cluster placement that produces the `recovered`, `partial` and `lost` outcomes. Requirements 5 and 6 fix the outcomes, not the placement.
- Whether the content checks live under `src/` next to the content builders. Requirement 10, criterion 9 requires them to be functions over image bytes that run on Fresh_Images in memory; the design chooses the module layout. The agent never runs the Generator, so the design cannot rely on a file in `public/disks/` to prove the contents.
- The site is assumed to be served from the site root, because the graveyard-ui contract fixes demo URLs at `/disks/<file>`.

## Glossary

- **Generator**: The script `scripts/make-demo-disks.ts` and the modules it calls, which produce the Demo_Disks.
- **Demo_Disk**: One of the three committed image files in `public/disks/`.
- **Writers_Disk**: The Demo_Disk `public/disks/writers-disk.img`.
- **Office_Disk**: The Demo_Disk `public/disks/office-disk.img`.
- **Damaged_Disk**: The Demo_Disk `public/disks/damaged-disk.img`.
- **Disks_Folder**: The directory `public/disks/`, the only place the Generator writes.
- **Image_Writer**: `writeFat12Image` and its types in `src/test-support/fat12/index.ts`.
- **Fixture_Writers**: `writeWordStar`, `writeDbf` and `encodePcx` in `src/test-support/formats/index.ts`.
- **Reader**: `openDisk` from `src/core/fat12/index.ts`, with the grader behind it. It returns a `DiskReport` with `Grave` entries and `Warning` entries.
- **Converter**: `convertAuto` from `src/core/formats/index.ts`.
- **Reader_Path**: The path under which the Reader lists a file. For a deleted file the first character of the name is replaced by `_`: `DRAFT1.WS` is `/_RAFT1.WS`, `DRAFT2.WS` is `/_RAFT2.WS`, `OLDCUST.DBF` is `/_LDCUST.DBF`. Converter name hints for deleted files use the Reader_Path name.
- **Grave**: A `Grave` object of the Reader: `id`, `path`, `size`, `date`, `state`, `kind`, `reason`, `startCluster`.
- **Grave_State**: One of `alive`, `recovered`, `partial`, `lost`.
- **Max_Image_Bytes**: `MAX_IMAGE_BYTES`, 2,949,120 bytes (2.88 MB), exported by `src/core/fat12/index.ts`.
- **Demo_Registry**: `DEMO_REGISTRY` in `src/web/demos.ts`.
- **Demo_Entry**: One `DemoDisk` object (`id`, `title`, `description`, `url`) in the Demo_Registry.
- **Committed_Image**: The bytes of a Demo_Disk as stored in the repository.
- **Fresh_Image**: The bytes the Generator produces for a Demo_Disk in memory, without writing a file.
- **Authored_Content**: Text, table rows and pixels written in the source of this repository, not copied from any third party.
- **Phone_Pattern**: A run of three ASCII digits, an ASCII hyphen and four ASCII digits that is not preceded and not followed by another ASCII digit, and that is not preceded or followed by a hyphen which is itself adjacent to a digit. Dates such as `1989-03-14` and amounts therefore do not match. A match is valid only when the three-digit prefix is `555` and the four-digit part is `0100` to `0199`.
- **Phone_Scope**: The text to which the Phone_Pattern check applies: the values of every character field of `CUSTOMER.DBF` whose name contains `PHONE`, the free text of every WordStar file, and the text of every `README.TXT`. Date fields, numeric fields, amounts, record numbers, invoice numbers, other DBF fields and binary files (PCX) are outside the Phone_Scope.
- **Shared_Checks**: The content checks of Requirement 10, criterion 9, each implemented as a function over image bytes.
- **Demo_Marker**: The volume label of a Demo_Disk plus a plain-text file `README.TXT` in its root that states the disk was generated by the Exhume demo-disk script.

## Requirements

### Requirement 1: Scope, reuse and dependencies

**User Story:** As the maintainer, I want the demo disks to be a thin layer over the finished writer, reader and converters, so that nothing already tested changes and nothing new is trusted.

#### Acceptance Criteria

1. THE Generator SHALL build every Demo_Disk image by calling the Image_Writer, and SHALL build the bytes of every WordStar, dBase III and PCX file by calling the Fixture_Writers.
2. THE Generator SHALL leave every existing file under `src/core/` and every existing file under `src/test-support/` unchanged, and SHALL add under `src/test-support/` only the new files `demo-source-scan.ts` and its test.
3. THE Generator SHALL add no entry to `dependencies`, `devDependencies` or `optionalDependencies` in `package.json`, and SHALL import no package other than Node built-in modules written with the `node:` prefix and the in-repository modules named in the Introduction.
4. THE Generator SHALL import nothing from `src/core/` except, where the Generator verifies its own output, the public modules `src/core/fat12/index.ts` and `src/core/formats/index.ts`.
5. THE Generator SHALL use no network API, no `child_process`, no `eval`, no dynamic `import()` and no environment variable to change its output.
6. THE repository SHALL contain an automated test that scans every non-test source file of the Generator and fails if the text contains `fetch`, `XMLHttpRequest`, `WebSocket`, `node:http`, `node:https`, `node:net`, `node:child_process`, `eval(`, `new Function`, `Date.now`, `new Date`, `Math.random`, `crypto.random` or `process.env`, printing the file path, the 1-based line number and the matched name for each violation.
7. WHEN the scan of criterion 6 is given a fixture string that holds each listed name, THE scan SHALL report one violation for each name, and WHEN it is given a fixture string that holds none of them, THE scan SHALL report zero violations.

### Requirement 2: Generator command and output location

**User Story:** As the maintainer, I want one command that regenerates the disks and writes only into one folder, so that I can rebuild them without risk to the rest of the repository.

#### Acceptance Criteria

1. THE `package.json` SHALL define an npm script `make:demos` that runs the Generator using only installed dependencies and Node 22 or later.
2. WHEN `npm run make:demos` runs, THE Generator SHALL write the Writers_Disk, the Office_Disk and the Damaged_Disk to `writers-disk.img`, `office-disk.img` and `damaged-disk.img` in the Disks_Folder, and SHALL create the Disks_Folder when it does not exist.
3. THE Generator SHALL write to no path other than the three files of criterion 2, and SHALL NOT delete, rename or change any other file in the Disks_Folder or elsewhere.
4. WHEN `npm run make:demos` runs with the argument `--check`, THE Generator SHALL write no file, SHALL compare each Fresh_Image with the Committed_Image of the same name, and SHALL exit with status 1 and print the name of each differing or missing file when any differs or is missing.
5. WHEN `npm run make:demos` runs with the argument `--check` and all three Committed_Images equal their Fresh_Images, THE Generator SHALL exit with status 0.
6. IF `npm run make:demos` runs with an argument other than none or `--check`, THEN THE Generator SHALL write nothing, print a fixed usage line and exit with status 1.
7. IF a Fresh_Image cannot be built because the Image_Writer or a Fixture_Writer throws, THEN THE Generator SHALL write none of the three files, print the name of the failing Demo_Disk and the error message, and exit with status 1.
8. THE Generator SHALL write each file only after all three Fresh_Images have been built, so that a failure while building leaves the Committed_Images unchanged.
9. THE `npm run build` script SHALL keep its current behavior and SHALL NOT run the Generator.
10. THE agent SHALL NOT run `npm run make:demos`, with or without `--check`, and SHALL NOT write, create or modify any file in the Disks_Folder; the user SHALL run the Generator the first time, after reviewing the Generator code, and SHALL commit the resulting images. The agent SHALL verify the disk contents only on Fresh_Images in memory, as Requirement 10, criterion 9 requires.
11. THE root `tsconfig.json` SHALL add `"scripts"` to its `include` list so that `scripts/make-demo-disks.ts` is type-checked, and SHALL change nothing else.

### Requirement 3: Byte-for-byte determinism

**User Story:** As a reviewer, I want the same bytes on every run and every machine, so that a diff of `public/disks/` always means the content changed on purpose.

#### Acceptance Criteria

1. THE Generator SHALL produce, for each Demo_Disk, a Fresh_Image that depends only on the source files of the repository.
2. THE Generator SHALL take no input from the clock, the time zone, the locale, random numbers, the host name, the user name, the working directory, the platform, directory listing order or the process environment.
3. THE Generator SHALL give every directory entry of every Demo_Disk an explicit fixed `modified` value, and SHALL give every Demo_Disk an explicit fixed volume serial number through the `serial` option of the Image_Writer.
4. WHEN the Generator builds the Fresh_Images twice in the same process, THE Generator SHALL produce two byte-identical images for each Demo_Disk.
5. THE Generator SHALL produce Fresh_Images whose bytes depend on no value other than the fixed content, dates and serial numbers in its source, so that two machines running the same commit produce identical files.
6. THE repository SHALL contain an automated test that builds all Fresh_Images twice and fails if any pair differs.
7. THE repository SHALL contain an automated test that fails if any Committed_Image differs from its Fresh_Image, with a message that tells the user to run `npm run make:demos` and commit the result. This test is a Committed_Image test under Requirement 10, criterion 10, and may fail until the user has generated and committed the images.
8. THE Generator SHALL write each Committed_Image as the exact bytes of the Fresh_Image, with no added header, trailer, line-ending change or compression.

### Requirement 4: Image validity and size bounds

**User Story:** As a judge, I want every demo disk to open cleanly the first time, so that the demo never breaks on the files we ship.

#### Acceptance Criteria

1. THE Generator SHALL build each Demo_Disk with a standard geometry name accepted by the Image_Writer (`StandardGeometryName`) that is not larger than `1440K`.
2. THE Generator SHALL produce each Demo_Disk with a length that is at most Max_Image_Bytes (2,949,120 bytes) and at most 1,474,560 bytes.
3. THE Generator SHALL produce each Demo_Disk with a length equal to the capacity of its geometry, so that the Reader can match the geometry by size where the BPB is invalid.
4. WHEN the Reader opens the Writers_Disk or the Office_Disk, THE Reader SHALL report `volume.geometrySource` equal to `bpb`.
5. WHEN the Reader opens the Writers_Disk or the Office_Disk, THE Reader SHALL report zero warnings.
6. THE Demo_Disks SHALL contain no more than 64 directory entries in total each, no directory deeper than 2 levels, and no file larger than 64 KiB, so that every Demo_Disk stays far below the reader limits.
7. THE repository SHALL contain an automated test that checks the length, geometry source and warning count of criteria 2 to 5 as a Shared_Check (Requirement 10, criterion 9) on the Fresh_Images in memory and, as a Committed_Image test (Requirement 10, criterion 10), on the Committed_Images, and that the sum of the three lengths is at most 4,423,680 bytes.
8. IF the Image_Writer throws a `FitError` while the Generator builds a Demo_Disk, THEN THE Generator SHALL treat the error as the build failure of Requirement 2, criterion 7.

### Requirement 5: The Writers_Disk

**User Story:** As a writer with a box of old floppies, I want a demo disk that looks like mine, so that I can see my chapters rise as Markdown and see an honest answer for the drafts I deleted.

#### Acceptance Criteria

1. THE Writers_Disk SHALL carry the volume label `WRITER DEMO`.
2. THE Writers_Disk SHALL hold at least three live WordStar files named `CHAPTER1.WS`, `CHAPTER2.WS` and `CHAPTER3.WS` in the root, built with `writeWordStar` from Authored_Content, each between 2,048 and 16,384 bytes, so that each file spans at least two clusters.
3. THE live WordStar files together SHALL use at least one bold span, one underline span, one italic span, one dot command line and one soft return, so that the Markdown output shows each of those WordStar features.
4. WHEN the Converter converts `CHAPTER1.WS` with the name hint `CHAPTER1.WS`, THE Converter SHALL return a Markdown result (`ok` true) that contains at least one paragraph of the authored text and at least one Markdown emphasis marker.
5. THE Writers_Disk SHALL hold a deleted file (written as `DRAFT1.WS`, listed by the Reader as `/_RAFT1.WS`) that the Reader grades `recovered`, whose size spans at least three clusters, and whose reason is non-empty.
6. THE Writers_Disk SHALL hold a deleted file (written as `DRAFT2.WS`, listed by the Reader as `/_RAFT2.WS`) that the Reader grades `partial`, whose first one or two clusters are free and unclaimed and whose next cluster is allocated to a live file, so that the file is partially overwritten, and whose reason is non-empty.
7. THE Writers_Disk SHALL hold the file `README.TXT` of the Demo_Marker, which the Reader grades `alive`.
8. WHEN the Reader reads the bytes of `/_RAFT1.WS` through the `DiskHandle`, THE Reader SHALL return `ok` true and exactly as many bytes as the declared size, and WHEN the Converter converts those bytes with the name hint `_RAFT1.WS`, THE Converter SHALL return a Markdown result (`ok` true) whose text equals the Markdown of the same authored paragraphs produced by the Converter from the `writeWordStar` bytes before they were written to the disk.
9. WHEN the Reader reads the bytes of `/_RAFT2.WS` through the `DiskHandle`, THE Reader SHALL return `ok` true with fewer bytes than the declared size, and WHEN the Converter converts those bytes with the name hint `_RAFT2.WS`, THE Converter SHALL return a result with `ok` true and non-empty text.
10. THE Writers_Disk SHALL hold exactly two files with state `recovered` or `partial` among its deleted files, and no file with state `lost`.
11. WHEN the Reader opens the Writers_Disk, THE Reader SHALL report `alive` for every file that is not deleted, with no `reason`.

### Requirement 6: The Office_Disk

**User Story:** As a small-business owner or an archivist, I want a demo disk with a customer table and a logo, so that I can see a `.DBF` become CSV, a `.PCX` become PNG, and a lost file reported as lost.

#### Acceptance Criteria

1. THE Office_Disk SHALL carry the volume label `OFFICE DEMO`.
2. THE Office_Disk SHALL hold a live file `CUSTOMER.DBF` in the root, built with `writeDbf` from Authored_Content, with at least five fields that include a character field, a numeric field, a date field and a character field whose name contains `PHONE` whose every value is a match of the Phone_Pattern in the range 555-0100 to 555-0199, and with at least 12 records.
3. THE records of `CUSTOMER.DBF` SHALL include at least one character value with a code page 437 character above 0x7F (for example an accented letter), so that the CSV output shows the code page 437 to UTF-8 conversion.
4. WHEN the Converter converts `CUSTOMER.DBF` with the name hint `CUSTOMER.DBF`, THE Converter SHALL return a CSV result (`ok` true) with one header row and exactly as many data rows as the table has records, and the CSV parsed with `parseCsv` SHALL equal the authored field names and record values.
5. THE Office_Disk SHALL hold a live file `LOGO.PCX` in the root, built with `encodePcx` from authored pixels, with a width of at most 256 pixels, a height of at most 256 pixels, and at least 4 distinct colors.
6. WHEN the Converter converts `LOGO.PCX` with the name hint `LOGO.PCX`, THE Converter SHALL return a PNG result (`ok` true) that `decodePng` decodes to the authored width, the authored height and the authored pixels.
7. THE Office_Disk SHALL hold one subdirectory `INVOICES` in the root with at least one live file in it, so that the graveyard shows a path with a directory part.
8. THE Office_Disk SHALL hold a deleted file (written as `OLDCUST.DBF`, listed by the Reader as `/_LDCUST.DBF`) that the Reader grades `lost`, whose start cluster is allocated to a live file, and whose reason is non-empty.
9. WHEN the Reader reads the bytes of `/_LDCUST.DBF` through the `DiskHandle`, THE Reader SHALL return the result the Reader defines for a `lost` file, and THE Office_Disk SHALL contain no assertion that those bytes convert.
10. THE Office_Disk SHALL hold the file `README.TXT` of the Demo_Marker, which the Reader grades `alive`.
11. WHEN the Reader opens the Office_Disk, THE Reader SHALL report `alive` for every file that is not deleted, with no `reason`.

### Requirement 7: The Damaged_Disk

**User Story:** As a judge, I want a demo disk that is broken in two known ways, so that I can see the page report warnings and still show what it can read.

#### Acceptance Criteria

1. THE Damaged_Disk SHALL carry the volume label `DAMAGE DEMO`.
2. THE Damaged_Disk SHALL be built with the `invalid-bpb` damage of the Image_Writer on exactly one BPB field, so that the BPB fails the Reader's validation while the image length still matches a fallback geometry.
3. WHEN the Reader opens the Damaged_Disk, THE Reader SHALL report `volume.geometrySource` equal to `fallback` and a warning with code `bpb-invalid`.
4. THE Damaged_Disk SHALL be built with the `cyclic-chain` damage on one live file of at least two clusters, named `LETTER.WS`, together with the `size-exceeds-chain` damage on the same file, so that the declared size is larger than the bytes the chain covers and the Reader follows the chain back to the repeated cluster; the two damages on `LETTER.WS` together count as one defect, the looping chain.
5. WHEN the Reader opens the Damaged_Disk, THE Reader SHALL report a warning with code `chain-cycle` whose `path` is `/LETTER.WS`, and SHALL grade `/LETTER.WS` as `partial` with a non-empty reason.
6. THE Damaged_Disk SHALL hold at least one live file, other than `LETTER.WS`, that the Reader grades `alive`, so that the page has something to show besides the damage.
7. THE Damaged_Disk SHALL hold the file `README.TXT` of the Demo_Marker, which states which two defects were introduced on purpose.
8. WHEN the Reader opens the Damaged_Disk, THE Reader SHALL return a report and SHALL NOT throw.
9. WHEN the Reader reads the bytes of `LETTER.WS` through the `DiskHandle`, THE Reader SHALL return a result in finite time, and THE result SHALL carry at most the declared size in bytes.
10. THE Damaged_Disk SHALL contain exactly two defects, the invalid BPB field of criterion 2 and the looping chain of `LETTER.WS` of criterion 4 (the `cyclic-chain` damage plus the `size-exceeds-chain` damage on that one file, because a cyclic chain alone is not seen by the Reader when the chain covers the declared size), and no other defect, so that the warnings on the Damaged_Disk are exactly the ones those two defects cause.

### Requirement 8: Authorship, honesty and safe content

**User Story:** As the maintainer, I want every demo file to be ours and labeled as generated, so that no one can mistake the demo for archive material or for a claim about prior art.

#### Acceptance Criteria

1. THE Generator SHALL take the content of every file on every Demo_Disk from Authored_Content in its own source, and SHALL read no file from outside the repository sources of the Generator.
2. THE Authored_Content SHALL contain no text copied from a third-party work, no real person's name, no real company name, no real address, no real phone number and no real e-mail address. Names, businesses and phone numbers SHALL be fictional, and every match of the Phone_Pattern within the Phone_Scope SHALL use the reserved range 555-0100 to 555-0199.
3. THE Authored_Content SHALL contain no secret, token, key or credential.
4. THE Demo_Marker SHALL be present on every Demo_Disk, and the `README.TXT` of every Demo_Disk SHALL state in plain ASCII that the disk was generated by the Exhume demo-disk script and that its content was written for the demo.
5. THE Demo_Disks SHALL hold no file whose extension is `EXE`, `COM`, `BAT`, `SYS`, `SCR`, `PIF`, `VBS` or `JS`, and no boot code in the boot sector beyond what the Image_Writer writes, so that nothing on a Demo_Disk is executable.
6. THE README of the repository SHALL state that the demo images in `public/disks/` are generated by `scripts/make-demo-disks.ts`, that the content is authored by the project, that they are not recovered archive material, and how to regenerate and check them (`npm run make:demos` and `npm run make:demos -- --check`).
7. THE README text about the demo disks SHALL NOT claim that Exhume is the first browser tool to browse or undelete FAT12 images, and SHALL leave the prior-art credit that `product.md` requires intact wherever the README discusses undelete.
8. THE repository SHALL contain an automated Shared_Check (Requirement 10, criterion 9) that reads the files of the Writers_Disk, the Office_Disk and the Damaged_Disk through the Reader and fails if any live or deleted file has one of the forbidden extensions of criterion 5, if a `README.TXT` lacks the statement of criterion 4, or if a volume label differs from the labels in Requirements 5 to 7.
9. THE repository SHALL contain an automated Shared_Check (Requirement 10, criterion 9) with three rules. Rule one: it fails if any text of any Demo_Disk, converted or read as plain text, contains `http://`, `https://`, `www.` or an e-mail address pattern (`@` between two letters); this rule applies to all text, including every DBF field. Rule two: it fails if any match of the Phone_Pattern within the Phone_Scope has a prefix other than `555` or a four-digit part outside `0100` to `0199`; this rule does not apply to date fields, numeric fields, amounts, record numbers, invoice numbers, other DBF fields or binary files. Rule three: the matcher SHALL run in linear time by a single left-to-right scan without a backtracking-prone regular expression, and SHALL examine at most 1,048,576 characters per text, reporting a failure for any text longer than that cap.

### Requirement 9: Web registry integration

**User Story:** As a visitor, I want the demo disks one click away on the page, so that I can see Exhume work without owning a floppy image.

#### Acceptance Criteria

1. THE Demo_Registry SHALL hold exactly three Demo_Entries, in this order: the Writers_Disk, the Office_Disk, the Damaged_Disk.
2. THE Demo_Entry for each Demo_Disk SHALL have an `id` equal to `writers-disk`, `office-disk` and `damaged-disk` respectively, a `url` equal to `/disks/writers-disk.img`, `/disks/office-disk.img` and `/disks/damaged-disk.img` respectively, a `title` of 1 to 80 characters, and a one-line `description` of 1 to 200 characters.
3. THE `description` of each Demo_Entry SHALL say in plain words what the visitor will see: for the Writers_Disk, WordStar chapters and two deleted drafts; for the Office_Disk, a customer table, a logo and a lost file; for the Damaged_Disk, a broken disk that produces warnings.
4. WHEN `validateDemoDisk` checks each Demo_Entry, THE function SHALL return `ok` true.
5. THE change to `src/web/demos.ts` SHALL be limited to the content of the Demo_Registry and the comment above it, and SHALL leave `loadDemoBytes`, its request options and every import unchanged.
6. THE change to existing web tests SHALL be limited to exactly two minimal edits, because those tests assume an empty registry: in `src/web/demos.test.ts` the empty-registry test SHALL assert the three Demo_Entries instead, and in `src/web/dom/demo-slot.dom.test.ts` the test that uses the default registry SHALL pass an explicit empty array as the registry; THE change SHALL touch no other web test and no other web source file, and THE Demo_Entries SHALL keep the existing web source scans and tests passing, including the scan that allows `fetch` only in `src/web/demos.ts` and the CSP rules of `safety.md`.
7. THE repository SHALL contain an automated test that, for each Demo_Entry, resolves the `url` to a file under `public/` and fails if the file is missing, if its length differs from the length of the Fresh_Image, or if it is larger than the web page's demo size cap (Max_Image_Bytes). This test is a Committed_Image test under Requirement 10, criterion 10, and may fail until the user has generated and committed the images.
8. WHEN `npm run build` completes, THE build output SHALL contain `dist/disks/writers-disk.img`, `dist/disks/office-disk.img` and `dist/disks/damaged-disk.img`, each byte-identical to the Committed_Image. The agent SHALL NOT run `npm run build` to check this unless the user asks; the check is left to the user or to the existing build tests.
9. THE Demo_Entries SHALL point only to same-origin paths that begin with `/disks/`, with no scheme, host or query string.

### Requirement 10: Verification through the existing reader, grader and converters

**User Story:** As a maintainer, I want the demo disks checked by the same code that users run, so that a change to the reader or a converter that breaks a demo is caught by `npm test`.

#### Acceptance Criteria

1. THE repository SHALL contain automated tests that open each disk image with the Reader, as the Shared_Checks of criterion 9 on the Fresh_Images and, through criterion 10, on the Committed_Images, and check the expected Grave paths, `kind`, `state`, `size` and presence or absence of `reason` of Requirements 5 to 7.
2. THE tests SHALL check the Grave states as an exact table: for each Demo_Disk, the set of `(path, state)` pairs equals the expected set, with no extra and no missing Grave other than the directory entry `INVOICES` and the entries that the Reader generates for subdirectories.
3. THE tests SHALL check the warnings of each Demo_Disk as an exact set of `code` values: no warnings for the Writers_Disk and the Office_Disk, and for the Damaged_Disk exactly the codes of Requirement 7, criteria 3 and 5 (a code may appear on more than one path only if the Reader reports it that way).
4. THE tests SHALL check each convertible file with the Converter as specified in Requirements 5 and 6, comparing the output with the output of the same Converter on the bytes that the Fixture_Writer produced before the bytes went to the disk.
5. WHEN the Reader and the Converter are run over every Grave of every Committed_Image whose state is not `lost`, THE Reader and THE Converter SHALL return without throwing, and every `ok` false result SHALL belong to a file the tests list explicitly as expected to fail or not convert.
6. THE tests SHALL run under `npm test` (Vitest), SHALL carry no `expect` call inside a fast-check property callback, and SHALL use `numRuns(base)` from `src/test-support/runs.ts` for any run count.
7. THE Committed_Image tests SHALL read the Committed_Images from the repository, no test SHALL write a file into the Disks_Folder or elsewhere in the repository, any temporary file the tests need SHALL live under `os.tmpdir()` and SHALL be removed by the test.
8. THE verification of this spec SHALL be example-based for the disk contents, because the input set is three fixed files, and SHALL include one fast-check property over the pure content builders only if the design introduces a builder with an input space (for example a generic table or pixel builder). If the design adds no such builder, no property test is required.
9. THE repository SHALL implement every content check of Requirements 3 to 9 and of criteria 1 to 5 of this requirement (Grave paths, kinds, states, sizes and reasons; warning codes; volume labels; `README.TXT` statements; forbidden extensions; Converter comparisons; the URL, e-mail and Phone_Pattern scan; length, geometry source and warning count) as a function over image bytes, and SHALL run each such function in an automated test on the Fresh_Images held in memory, so that the disk contents are proven before any file exists in the Disks_Folder.
10. THE Committed_Image tests SHALL be limited to: the equality of committed bytes and fresh bytes (Requirement 3, criterion 7), the file length checks (Requirement 4, criterion 7 and Requirement 9, criterion 7), and running the same Shared_Checks of criterion 9 on the Committed_Image bytes.
11. WHEN `npm test` runs with no file in the Disks_Folder, THE in-memory tests of criterion 9 SHALL pass, and only the Committed_Image tests of criterion 10 MAY fail.
12. IF a Committed_Image test fails because a Committed_Image is missing or differs from its Fresh_Image, THEN THE test SHALL print a message that tells the user to run `npm run make:demos` and commit the result.

### Requirement 11: Documentation

**User Story:** As a reader of the repository, I want to know what the demo disks are and how to rebuild them, so that I can trust them and reproduce them.

#### Acceptance Criteria

1. THE README SHALL list the three Demo_Disks by file name with one sentence each on what the disk shows, including the expected Grave_State of each deleted file.
2. THE README SHALL name `npm run make:demos` as the way to regenerate the disks and `npm run make:demos -- --check` as the way to verify that the committed files match the script.
3. THE README SHALL state the determinism rule of Requirement 3 in one sentence: the same commit produces the same bytes.
4. THE README SHALL state that the Damaged_Disk is broken on purpose in two ways and name them (a bad BPB field and a cyclic cluster chain).
5. THE implementation of this spec SHALL append lines about this spec to `docs/KIRO_LOG.md` only when the user asks.
