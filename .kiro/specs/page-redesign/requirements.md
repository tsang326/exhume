# Requirements Document

## Introduction

The Spec 9 page works but reads as wordy and flat: one monospace face, no typographic hierarchy, an intro list that reads like steps, and a modal preview dialog. The project owner approved a mockup (`docs/design/redesign/mockup.html`, screenshots in `docs/design/redesign/screens/` at 1440, 768 and 390 px). This spec turns the Page into that design while keeping every safety rule and the behaviour of the existing app.

The redesign has these parts: two self-hosted typefaces and a new palette; a hero with an inline disk photo; a row of headstones for the writer's demo disk; a strata background (inline SVG, flat fills, a tiled grain image); an always-populated demo section; an inline two-column graveyard and preview in place of the dialog; a "Deleted is not the same as gone." bar; a photo band and a formats section; a footer with a half-buried serif "Exhume"; and a small set of motions.

Scope is `index.html`, `src/style.css`, `src/web/` and their tests, plus new static assets (fonts under `src/assets/fonts/`, images, grain). Out of scope: new formats, changes to `src/core/`, `src/mcp/`, `power/`, the worker protocol, the demo disk generator and the demo disks themselves, the Crew app, deployment, video.

The steering rules apply (`.kiro/steering/product.md`, `safety.md`, `tech.md`):

- The CSP in `index.html` stays exactly as it is. The mockup uses an inline `<style>` element and inline `style` attributes; the Page cannot, so all styling lives in `src/style.css`.
- Text from a Disk_Image enters the DOM with `textContent` or Text nodes only, never `innerHTML`.
- Nothing is fetched from another origin, and no font, script or image is external.
- No new runtime dependency is added.
- Nothing is placed under `public/fonts/` (that path is blocked on the owner's machine).
- Public text follows the honesty rules: prior art (andete/disk-peek) is credited, claims match the README, and the demo disks are said to be generated by our own script.

## Glossary

- **Page**: The static web page built from `index.html`, `src/main.ts`, `src/style.css` and `src/web/`.
- **Element_Contract**: The comment in `index.html` that lists the element ids `src/main.ts` and `src/web/app.ts` look up, together with the behaviour tied to each id.
- **Retained_Ids**: The ids `app`, `drop-zone`, `pick-button`, `file-input`, `status`, `cancel-button`, `reopen-button`, `demo-slot`, `graveyard`, `privacy-note`, `honesty-note` and `repo-link`.
- **Retiring_Ids**: The ids `intro`, `fx-host` and `preview-root`, which served the Spec 9 intro block, the canvas effects layer and the preview dialog.
- **Disk_Image**: An untrusted byte sequence that the user drops, chooses or loads as a demo.
- **Untrusted_Text**: Any text derived from a Disk_Image: file names, volume labels, reasons, warnings, converted document text, CSV cells.
- **Demo_Disks**: The three images in `public/disks/`, produced by `scripts/make-demo-disks.ts`.
- **Writer_Disk**: The Demo_Disk with id `writers-disk`, the writer's demo disk.
- **Demo_Report**: The `DiskReport` that the reader returns for a Demo_Disk, read at test time from the committed image.
- **Demo_Check**: The command `npm run make:demos -- --check`.
- **Display_Face**: Instrument Serif, weight 400, normal style only (no italic file is shipped), used for headings only.
- **Text_Face**: Hanken Grotesk, variable weight, used for all other text.
- **Preview_Face**: The monospace face, allowed only inside the plain-text preview and the hex view.
- **Palette_Tokens**: The CSS custom properties in the `:root` of the mockup: night `#0b0f10`, soil layers, bone paper field, amber accent `#ffbf5e`, and the state colours alive, recovered, partial and lost.
- **Contrast_Pair**: A foreground and background colour pair declared in `src/style.css` as `--pair-<id>-fg` and `--pair-<id>-bg`, and checked by the contrast tests.
- **Hero**: The first section: nav, headline, supporting sentence, open button, demo link, extension line and privacy line.
- **Disk_Photo**: `disk35.jpg`, shown inline in the headline as a decorative image with empty `alt`.
- **Open_Button**: The visible button `#pick-button`, styled as the amber "Open a disk image" button.
- **Extension_Line**: The Hero line that lists `.img`, `.ima`, `.vfd`, `.flp` and `.dsk` and the 2.88 MB limit.
- **Headstone_Row**: The row of headstones on the ground line under the Hero. It shows the writer's disk: exactly the six files of the Writer_Disk, in report order (`CHAPTER1.WS`, `_RAFT1.WS`, `CHAPTER2.WS`, `_RAFT2.WS`, `CHAPTER3.WS`, `README.TXT`).
- **Headstone**: One stone in the Headstone_Row.
- **Strata**: The decorative background layers: night surface, soil layers with irregular edges, a torn paper edge, a soil edge and a tiled grain image.
- **Decorative_Layer**: Any Strata element or other purely decorative element. Each is `aria-hidden` and never covers text.
- **Demo_Section**: The section with the heading "No disk? Open one of ours." and one Demo_Card per Demo_Disk.
- **Demo_Card**: One `button` in the Demo_Section with its drawn floppy, title and description.
- **Graveyard_Panel**: The left column of the inline layout: volume label, counts, warnings banner and grave rows.
- **Grave_Row**: One entry of the Graveyard_Panel for a file or deleted entry.
- **Preview_Panel**: The right column of the inline layout that replaces the Spec 9 preview dialog. It shows the converted file on the paper field.
- **Paper_Field**: The bone-coloured surface (`--field`) used by the Preview_Panel and the Formats_Section.
- **State_Word**: The visible word for a file state, returned by the single function `stateWord()`: "Alive", "Recovered", "Partly back" or "Lost". Grave_Rows, Headstones and the Disk_Bar take their state text only from this function.
- **Auto_Open**: The automatic open of the Writer_Disk, and the automatic preview of `CHAPTER1.WS`, that the Page performs on load when no disk is open.
- **User_Open**: Any open started by a user action: the Open_Button, the footer open control, a drop, the file chooser, a Demo_Card or a Headstone.
- **Byte_Totals**: The four figures of the Disk_Bar, computed from the Demo_Report. Alive is the sum of declared sizes of alive files. Recovered is the sum of declared sizes of recovered files. Partly back is the sum, over partial files, of the byte length that `readBytes` returns. Lost is the sum, over partial files, of the declared size minus that length, plus the sum of declared sizes of lost files. For the current Writer_Disk the values are 10,600, 3,468, 2,048 and 1,024 bytes.
- **Disk_Bar**: The segmented bar under the heading "Deleted is not the same as gone." for the Writer_Disk.
- **Photo_Band**: The three-disk photo `disks-band.jpg` with the caption "From 8 to 3½ inches." and the FAT12 160 KB–2.88 MB line.
- **Formats_Section**: The Paper_Field section "Files from 1989, readable today." with three rows: WordStar to Markdown, dBase III to CSV, PCX to PNG.
- **Footer**: The closing section with the invitation, links, photo credit, prior-art line and the buried name.
- **Buried_Name**: The large serif "Exhume" in the Footer, half hidden by a soil edge.
- **Reduced_Motion**: The browser state where `(prefers-reduced-motion: reduce)` matches.
- **Narrow_Viewport**: A viewport 760 CSS pixels wide or less, the breakpoint of the mockup.
- **Existing_Tests**: Every test that passes before this spec's changes, including `src/web/page.static.test.ts`, the DOM tests in `src/web/` and `src/web/dom/`, and `src/web/dist.build.test.ts`.
- **Verification_Suite**: `npm run typecheck`, `npm test`, `npm run test:dom`, `npm run build` and `npm run make:demos -- --check`.

## Requirements

### Requirement 1: Safety rules and CSP stay intact

**User Story:** As the project owner, I want the redesign to keep every safety rule, so that a hostile disk image cannot do harm through the new page.

#### Acceptance Criteria

1. THE Page SHALL keep the Content-Security-Policy meta element in `index.html` byte for byte identical to its content before this spec.
2. THE Page SHALL contain no inline `<style>` element, no `style` attribute, no inline script and no `on*` attribute in `index.html`.
3. THE Page SHALL load no font, script, stylesheet or image from another origin, and every `url()` and `src` in `src/style.css` and `index.html` SHALL resolve to a same-origin path.
4. THE Page SHALL place no file under `public/fonts/`.
5. THE Page SHALL add no entry to the `dependencies` of `package.json`.
6. THE Page SHALL insert Untrusted_Text into the DOM only through `textContent` or Text nodes.
7. FOR ALL Disk_Images, including those whose names, labels, reasons or converted text contain `<`, `>`, `&`, quotes or `<script>`, the rendered Page SHALL contain no element created from that text, so the count of elements in the Graveyard_Panel and the Preview_Panel depends only on the report structure (property).
8. THE source files under `src/web/` SHALL contain no use of `innerHTML`, `outerHTML`, `insertAdjacentHTML` or `document.write` on a path that receives Untrusted_Text.
9. THE Page SHALL send no byte of a Disk_Image to any network endpoint, and `fetch` SHALL remain used only in `src/web/demos.ts` for same-origin demo disk files.

### Requirement 2: Element contract and existing behaviour keep working

**User Story:** As a maintainer, I want the ids and hooks that existing code and tests rely on to keep working, so that the redesign does not break the app.

#### Acceptance Criteria

1. THE Page SHALL contain exactly one element for each id in the Retained_Ids.
2. THE Element_Contract SHALL list every id in the Retained_Ids and every id that this spec adds, with its role.
3. WHERE an id in the Retiring_Ids is removed from `index.html`, THE Element_Contract SHALL record that id as retired, and no code in `src/` SHALL look it up.
4. THE `#status` element SHALL keep `role="status"`, `aria-live="polite"` and `aria-atomic="true"`.
5. WHILE a worker request is pending, THE Page SHALL show `#cancel-button`; WHILE no request is pending, THE Page SHALL hide it.
6. WHILE the disk is lost and its bytes are held, THE Page SHALL show `#reopen-button`; WHEN the user activates it, THE Page SHALL reopen the held bytes.
7. WHEN the user drops a file anywhere on the Page, THE Page SHALL open it as a disk image through the same pipeline as a chosen file.
8. THE `#file-input` SHALL carry no `accept` attribute, so that the choice of file is not restricted by extension.
9. THE Existing_Tests SHALL pass after the change, and a test that checked retired behaviour (the intro list, the canvas effects layer, the dialog, its focus trap or `inert`) SHALL be rewritten for the replacement behaviour instead of being deleted without a successor.

### Requirement 3: Typography and palette

**User Story:** As a visitor, I want a clear typographic hierarchy, so that the page reads as designed rather than as a wall of monospace.

#### Acceptance Criteria

1. THE Page SHALL use the Display_Face for `h1`, `h2` and `h3` headings and the large Buried_Name, and the Text_Face for every other text.
2. THE Page SHALL use the Preview_Face only inside the plain-text preview and the hex view.
3. THE Page SHALL serve the Display_Face (normal style) and the Text_Face as self-hosted `woff2` files under `src/assets/fonts/`, bundled by Vite, and SHALL ship an italic Instrument Serif file only if a style in `src/style.css` uses it.
4. THE `src/assets/fonts/` folder SHALL contain the SIL Open Font License 1.1 text of each shipped face next to its font files.
5. THE `src/style.css` file SHALL define the Palette_Tokens with the values of the mockup.
6. THE `src/style.css` file SHALL define each font-face with `font-display: swap`.
7. FOR ALL text and background colour combinations that the redesign introduces, including text on the Paper_Field, muted text on soil layers, the amber button, the state labels on soil, and Headstone labels, `src/style.css` SHALL declare a Contrast_Pair, and the contrast tests SHALL require a ratio of at least 4.5:1 for text and 3:1 for UI components.
8. WHEN the font files fail to load, THE Page SHALL fall back to the system serif and system sans-serif stacks listed in the mockup, with no change in layout beyond glyph shapes and no horizontal scroll.

### Requirement 4: Hero

**User Story:** As a first-time visitor, I want a short, striking opening that says what Exhume does, so that I know within seconds whether it helps me.

#### Acceptance Criteria

1. THE Hero SHALL contain exactly one `h1` whose visible text reads "Dig up lost files." with the Disk_Photo as an inline image between "Dig up" and "lost files."
2. THE Disk_Photo SHALL carry `alt=""` as a decorative image, and the accessible name of the `h1` SHALL be exactly "Dig up lost files."
3. THE Hero SHALL contain one supporting sentence that says Exhume opens 1980s DOS floppy images in the browser and brings deleted files back as far as the disk allows.
4. THE Hero SHALL contain the Open_Button with the visible text "Open a disk image", styled in the amber accent.
5. WHEN the user activates the Open_Button, THE Page SHALL open the file chooser through `#file-input`.
6. THE Hero SHALL contain a link with the text "or try a demo disk" whose `href` targets the Demo_Section.
7. THE Extension_Line SHALL list `.img`, `.ima`, `.vfd`, `.flp` and `.dsk` and the text "up to 2.88 MB".
8. THE Hero SHALL contain the privacy line "Your files stay in this browser. Nothing is uploaded." in `#privacy-note`, of at most 140 characters.
9. THE Page SHALL contain a nav with the disk mark and the word "Exhume", and anchors named "Demo disks", "How it works", "Formats" and "GitHub", each of whose `href` resolves to an existing element id on the Page or to the Repo_Link target.
10. THE GitHub anchor SHALL have the `href` `https://github.com/tsang326/exhume`, and `#repo-link` SHALL keep that `href` and an accessible name that identifies the GitHub repository.
11. THE Page SHALL contain no capability list in the Hero.
12. THE Page SHALL contain each claim in the Hero and the meta description only in terms that the README supports, and no numeric figure that the README does not contain.
13. THE Page SHALL have the `<title>` "Exhume - read old floppy disks in your browser" and one non-empty `<meta name="description">` of at most 160 characters.

### Requirement 5: Headstone row

**User Story:** As a visitor, I want to see the writer's disk as a row of headstones, so that I can open a file with one click and see what "deleted" looks like.

#### Acceptance Criteria

1. THE Headstone_Row SHALL contain exactly six Headstones, one for each file of the Writer_Disk, in the order of the Demo_Report, and SHALL contain no Headstone for a file of another Demo_Disk.
2. FOR ALL Headstones, THE name and the State_Word SHALL equal the name and the `stateWord()` result that the view model derives from the Demo_Report entry (property over the Demo_Report entries).
3. WHEN a Headstone has the state `partial`, THE Page SHALL draw it with a dashed outline and a sunk position, and the State_Word text SHALL be present on every Headstone so that the state does not rely on colour alone.
4. WHEN a Headstone has the state `recovered`, THE Page SHALL animate it rising once on load.
5. THE Page SHALL render each of the six Headstones as a native `button`, and WHEN the user activates a Headstone, THE Page SHALL open the Writer_Disk and open that file in the Preview_Panel.
6. THE Headstone_Row SHALL have an accessible name that says it shows the writer's disk files.
7. IF the committed Writer_Disk changes so that a Headstone name or state no longer matches the Demo_Report, THEN THE headstone test SHALL fail.
8. WHILE the viewport is a Narrow_Viewport, THE Headstone_Row SHALL wrap its six Headstones onto several lines, SHALL keep all six visible, focusable and listed once, and SHALL not scroll horizontally.

### Requirement 6: Strata background and decorative layers

**User Story:** As a visitor, I want a layered earth look behind the content, so that the page feels like digging, without hurting readability.

#### Acceptance Criteria

1. THE Page SHALL draw the Strata as a night surface, soil layers with irregular edges drawn as inline SVG shapes with flat fills, a torn paper edge into the Formats_Section and a soil edge into the Footer.
2. THE Page SHALL overlay a subtle tiled grain image over the whole page, served from the same origin, with `pointer-events: none`.
3. THE Strata SHALL use no gradient fill, no glow and no blur.
4. FOR ALL Decorative_Layers, THE element SHALL carry `aria-hidden="true"` and `pointer-events: none`, and SHALL not overlap text in stacking order above it.
5. THE Page SHALL cover its whole scrollable height with background colour, so that no visible edge or flat band appears at any page length at 1440×900, 768×1024 and 390×844.
6. THE Page SHALL remove the canvas fog and lantern layer of Spec 9 (`#fx-host`, `src/web/dom/effects.ts`, `src/web/logic/effects-math.ts` and their tests) AND SHALL leave no reference to them in `src/web/app.ts`.
7. THE Page SHALL show no horizontal scroll at 1440, 768 and 390 px widths.
8. THE grain overlay opacity SHALL be the highest value from 0.22 down to 0.10 for which every text Contrast_Pair still passes when measured over the real grain texture; IF no value at or above 0.10 passes, THEN THE Page SHALL move the grain into the section backgrounds beneath the text.

### Requirement 7: Demo section open by default

**User Story:** As a visitor with no disk, I want the demo disks one click away and one already open, so that the page is never empty.

#### Acceptance Criteria

1. THE Demo_Section SHALL have the heading "No disk? Open one of ours." and one Demo_Card for each valid entry of the demo registry.
2. THE Demo_Card SHALL contain a drawn floppy as `aria-hidden` inline SVG, the disk title and its description: a blue 3.5-inch for the writer's disk, a red 5.25-inch for the small-business disk and a damaged disk with a torn label for the damaged disk.
3. THE Demo_Section SHALL state that the three demo disks are generated by our own script (`scripts/make-demo-disks.ts`) and are not real archive disks.
4. WHILE a Demo_Disk is the open disk, THE Demo_Card of that disk SHALL have `aria-pressed="true"` and every other Demo_Card SHALL have `aria-pressed="false"`; WHILE a disk opened from a file is open, every Demo_Card SHALL have `aria-pressed="false"`.
5. WHEN the Page finishes loading and no disk is open, THE Page SHALL perform the Auto_Open: open the Writer_Disk through the normal intake pipeline and preview `CHAPTER1.WS` in the Preview_Panel, without moving focus, without scrolling and without any `#status` announcement, with the Grave_Row of `CHAPTER1.WS` marked `aria-current="true"` and the Preview_Panel filled, so that a first-time visitor sees a filled preview.
6. WHEN a User_Open opens a disk, THE Page SHALL scroll the Demo_Section's graveyard into view, with instant scrolling under Reduced_Motion and smooth scrolling otherwise, and SHALL move focus to the graveyard heading; WHEN the User_Open is a Headstone activation, THE Page SHALL then move focus to the Preview_Panel heading and scroll the Preview_Panel into view, so that focus ends on the Preview_Panel heading.
7. IF the automatic open of the Writer_Disk fails, THEN THE Page SHALL show the failure message in `#status` and SHALL leave the Demo_Cards usable.
8. IF a User_Open or any other user action occurs before the Auto_Open or its automatic preview finishes, THEN THE Page SHALL drop or replace the automatic result, and the Page SHALL show the result of the user action and not the Writer_Disk or `CHAPTER1.WS` preview.
9. WHILE no disk is open, THE Graveyard_Panel SHALL show one line of guidance "Open a disk to see its files."

### Requirement 8: Graveyard and inline preview

**User Story:** As a user, I want the file list and the opened file side by side on the page, so that I can read files without a dialog hiding the list.

#### Acceptance Criteria

1. WHEN a disk is open, THE Page SHALL show the Graveyard_Panel and the Preview_Panel in two columns at widths above the Narrow_Viewport, and SHALL stack them with the Preview_Panel after the list on a Narrow_Viewport.
2. THE Graveyard_Panel SHALL show the volume label, the count of files and the count of deleted entries, and the warnings banner when the report has warnings.
3. THE Grave_Row SHALL show a stone icon, the name, the size, the date, the State_Word and the reason when the report gives one.
4. WHERE the name of a Grave_Row has a leading `_` from a deleted 8.3 entry, THE Grave_Row SHALL show a text hint that DOS overwrote the first letter on delete.
5. THE state of a Grave_Row SHALL be identified by its State_Word and a distinct stone shape, in addition to colour.
6. WHEN the user activates a Grave_Row whose action is `exhume`, THE Page SHALL run the existing rise-and-read flow and show the result in the Preview_Panel, with focus and announcement as set by criteria 17 and 18.
7. WHILE a file is open in the Preview_Panel, THE Grave_Row of that file SHALL have `aria-current="true"` and no other Grave_Row SHALL have it.
8. WHEN a user action opens a file in the Preview_Panel, THE Page SHALL announce the opened file in `#status` as set by criterion 17; the automatic preview of the Auto_Open SHALL make no announcement.
9. THE Preview_Panel SHALL show converted Markdown as a document, a CSV as a table, a PNG with `image-rendering: pixelated`, plain text as text and an unknown file as a hex view, all on the Paper_Field.
10. WHERE a file is `partial` or `lost`, THE Preview_Panel SHALL show a note at the place where the content stops.
11. THE Preview_Panel SHALL offer a download button labelled with the converted extension ("Download .md", "Download .csv", "Download .txt" or "Download .png") and a "Download raw bytes" button, through the existing downloader, with the fixed safe MIME types and sanitized names of `safety.md`.
12. THE Page SHALL contain no element with `role="dialog"` or `aria-modal`, and SHALL not set `inert` on `#app`.
13. THE Page SHALL keep a Tab order that follows the visual order: nav anchors, Open_Button, demo link, Headstones, Demo_Cards, Grave_Rows, Preview_Panel buttons, then the Footer controls.
14. WHEN the disk changes through a User_Open, THE Page SHALL revoke every Blob URL of the previous preview, and the Preview_Panel SHALL show its empty state; the automatic preview of the Auto_Open SHALL not be an exception for a User_Open, and a user action during the Auto_Open or its automatic preview SHALL always win over it.
15. FOR ALL reports and for ALL sequences of open-disk and open-file actions, THE number of live Blob URLs after the sequence SHALL be at most the number needed by the currently shown preview (property).
16. THE Preview_Panel SHALL cap the length of the text it shows with the existing limits and SHALL show the existing note when the text is shortened.
17. WHEN the user activates a Grave_Row on a layout wider than 760 CSS pixels, THE Page SHALL keep focus on that Grave_Row and SHALL announce "Opened NAME." in `#status`, where NAME is the file name as the Grave_Row shows it.
18. WHEN the user activates a Grave_Row on a Narrow_Viewport, THE Page SHALL move focus to the Preview_Panel heading and scroll the Preview_Panel into view, with instant scrolling under Reduced_Motion and smooth scrolling otherwise, and SHALL announce "Opened NAME." in `#status`.
19. WHEN the user activates a Headstone, THE Page SHALL move focus to the Preview_Panel heading and scroll the Preview_Panel into view at any viewport width, with instant scrolling under Reduced_Motion and smooth scrolling otherwise.

### Requirement 9: "Deleted is not the same as gone."

**User Story:** As a visitor, I want to see how much of a deleted disk can come back, so that I trust the honest grading.

#### Acceptance Criteria

1. THE Page SHALL show a section with the heading "Deleted is not the same as gone." and the Disk_Bar for the Writer_Disk.
2. THE Disk_Bar SHALL contain four segments in the order alive, recovered, partly back and lost, with widths proportional to the four Byte_Totals.
3. THE Disk_Bar SHALL show a short caption for each segment, placed beside the bar on wide viewports and inside the segments on a Narrow_Viewport, and each caption SHALL use the State_Word from `stateWord()` for its state.
4. FOR ALL states, THE figure shown in a segment SHALL equal the corresponding Byte_Total, formatted with the same shared size formatter as the Grave_Row (for example 10.4 KB for 10,600 bytes), and THE Disk_Bar SHALL not copy the figures of the mockup (property over the Demo_Report entries).
5. THE Disk_Bar SHALL expose one accessible text equivalent that names all four figures, and its segments and captions SHALL be `aria-hidden` where they would repeat that text.
6. WHEN the Disk_Bar scrolls into view, THE segments SHALL fill from the left in order, except under Reduced_Motion, where they SHALL appear filled.
7. IF the committed Writer_Disk changes so that a figure no longer matches, THEN THE figure test SHALL fail.
8. THE captions SHALL describe the grading truthfully: recovered means every cluster was still free, partly back means some clusters were free, lost means a later file overwrote the data.

### Requirement 10: Photo band and formats

**User Story:** As a visitor, I want to see what the three conversions look like on real demo content, so that I believe the page can read 1989 files.

#### Acceptance Criteria

1. THE Photo_Band SHALL show `disks-band.jpg` with a non-empty `alt` text, the heading "From 8 to 3½ inches." and a line that says any DOS floppy image with a FAT12 file system from 160 KB to 2.88 MB can be opened.
2. THE Formats_Section SHALL have the heading "Files from 1989, readable today." and three rows in this order: WordStar to Markdown, dBase III to CSV, PCX to PNG.
3. THE WordStar row SHALL show an excerpt of `CHAPTER1.WS` as converted by the core converter from the Writer_Disk.
4. THE dBase row SHALL show rows of `CUSTOMER.DBF` as converted by the core converter from the small-business demo disk, as a table, with figures shown exactly as the converter outputs them.
5. THE PCX row SHALL show `LOGO.PCX` from the small-business demo disk, converted to PNG and shown at an integer scale of 7× above 760 CSS pixels and 4× at or below 760 CSS pixels, with `image-rendering: pixelated` and a non-empty `alt` text.
6. FOR ALL excerpts and rows shown, THE text SHALL be a prefix or a row subset of the converter's output on the committed Demo_Disks, and the excerpt test SHALL fail when the output changes (property over the shown cells).
7. THE Page SHALL render the excerpts through `textContent` or Text nodes, or as static markup that a test has compared to the converter output.
8. THE Page SHALL state, near each excerpt, which demo disk and file it comes from.
9. THE Page SHALL copy `disk35.jpg` and `disks-band.jpg` from `docs/design/redesign/assets/` to a bundled asset location.

### Requirement 11: Footer, credits and honesty

**User Story:** As a judge or a visitor, I want the credits and prior art on the page, so that the project is honest about its sources.

#### Acceptance Criteria

1. THE Footer SHALL contain the line "Found an old disk in a drawer?" and a second visible control that opens the file chooser through `#file-input`.
2. THE Footer SHALL contain links named "Source on GitHub" (to `https://github.com/tsang326/exhume`), "Prior art: disk-peek" (to `https://github.com/andete/disk-peek`) and the plain text "Kiroween 2026", which is not a link.
3. THE Footer SHALL contain the photo credit "Floppy disk 2009 G1" by George Chernilevsky, public domain, via Wikimedia Commons, matching `docs/design/redesign/assets/credits.json`.
4. THE Page SHALL keep `#honesty-note` with a sentence that names andete/disk-peek as an existing browser tool for FAT12 images and deleted-entry recovery, and SHALL contain no claim of being the first browser undelete.
5. THE external links SHALL carry `rel="noopener noreferrer"`.
6. THE Buried_Name SHALL be `aria-hidden`, centred with equal left and right margins at every width from 320 to 1920 px, and SHALL cause no horizontal scroll.
7. THE Page SHALL credit the two typefaces and their licence (SIL OFL 1.1) in the Footer or in a linked licence file.

### Requirement 12: Motion

**User Story:** As a visitor sensitive to motion, I want all animation to stop when I ask for less motion, so that the page is safe to use.

#### Acceptance Criteria

1. THE Page SHALL use animation only for: the headline words rising on load, the Disk_Photo shutter, the recovered Headstone rising, section entrances, the Disk_Bar filling and a short fade when the Preview_Panel content changes.
2. WHILE Reduced_Motion is active, THE Page SHALL run no animation or transition, SHALL show the Disk_Photo, the headline, section content and the Disk_Bar fully visible, and SHALL scroll instantly.
3. IF scripting that adds entrance classes does not run, THEN THE Page SHALL still show all content visible.
4. THE Page SHALL animate only `opacity`, `transform` and `clip-path`.
5. WHILE an animation runs, THE Page SHALL keep every content element and control enabled, receiving pointer events and focusable, with no `disabled` attribute, no `pointer-events: none` and no `inert` on any of them.

### Requirement 13: Accessibility and responsive layout

**User Story:** As a keyboard or screen-reader user, I want the redesigned page to remain fully usable, so that the design does not cost access.

#### Acceptance Criteria

1. THE Page SHALL keep exactly one `h1`, a heading order without skipped levels, one `main` landmark and a `lang` attribute.
2. THE Page SHALL give each interactive element a visible focus outline with a Contrast_Pair of at least 3:1 against its background.
3. THE Page SHALL make every control operable by keyboard, with a native `button` or `a` for each action.
4. THE Page SHALL give each interactive target a hit area of at least 40 CSS pixels in height.
