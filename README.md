# Exhume

Your old disks aren't dead. They're buried.

Drop a DOS floppy image into the page and its files appear as a graveyard. Deleted files are open graves you can
dig up. WordStar documents rise as Markdown, dBase tables as CSV, PCX pictures as PNG, plain text files as `.txt` text. Everything runs in your
browser; nothing is uploaded.

The page reads 1980s-era DOS floppy images (FAT12) with the extensions `.img`, `.ima`, `.vfd`, `.flp` and `.dsk`, from
160 KB up to 2.88 MB. It is one page: a hero where you drop or pick a disk, a graveyard of headstones and file rows
below it, an inline preview beside the list, and demo disk cards you can open with one click.

Also ships as an MCP server / Kiro Power and a Kiro Crew app, so an agent can open a floppy image and exhume files
into your project.

Prior art: [disk-peek](https://github.com/andete/disk-peek) already browses FAT12 images and recovers deleted
entries in the browser.

Kiroween 2026, Resurrection category. Built with [Kiro](https://kiro.dev) (see `/.kiro` and `docs/KIRO_LOG.md`).

## Run
```bash
npm install
npm run dev      # http://localhost:5173
npm test
```

## Demo disks

The page offers three demo floppy images, kept in `public/disks/`. They are generated by
`scripts/make-demo-disks.ts`. The content is authored by the project: fictional names, fictional businesses and
phone numbers in the reserved 555-0100 to 555-0199 range. The images are not recovered archive material.

- `writers-disk.img` (360 KB, label `WRITER DEMO`): three WordStar chapters and two deleted drafts. `/_RAFT1.WS` is
  `recovered` and `/_RAFT2.WS` is `partial`.
- `office-disk.img` (720 KB, label `OFFICE DEMO`): a dBase customer table, a PCX logo, an invoice in a subfolder and a
  deleted old customer table. `/_LDCUST.DBF` is `lost`.
- `damaged-disk.img` (360 KB, label `DAMAGE DEMO`): a disk broken on purpose in two ways, a bad BPB field (sectors per
  cluster set to zero) and a cyclic cluster chain (`LETTER.WS` loops back on itself). Opening it produces warnings
  instead of a crash.

The first character of a deleted file name is lost when a DOS directory entry is deleted, so the Reader shows the
names with a leading underscore.

To regenerate the images, or to check that the committed files match the script:

```bash
npm run make:demos
npm run make:demos -- --check
```

The same commit produces the same bytes: there is no clock and no randomness in the generator. Each image carries a
`README.TXT` that says it was generated by the Exhume demo-disk script and written for the demo.

## Tested on real disks

Exhume was tested on 35 real DOS disks that are not part of the demo disks: 24 FreeDOS 1.3 floppy images and 11 disks from the PCjs archive (160 KB to 1.44 MB). The FreeDOS files were checked against the macOS msdos driver (read-only mount) and the PCjs files against the per-file MD5 table that PCjs publishes with each disk. All 942 files matched that independent reference byte for byte. 63 of the 63 PCX images that Pillow could open matched pixel for pixel; Pillow refused the other 25, which Exhume renders. 39 of 39 dBase III tables matched `dbfread`, with dates and logicals compared after normalising Exhume's ISO date and TRUE/FALSE output. The page does not offer these disks. Three unmodified FreeDOS images are kept in `fixtures/real-disks/freedos13/` as read-only test input, with their own license notice.

## MCP server and Kiro Power

Exhume ships as a local stdio MCP server (`power/server/exhume-mcp.mjs`) wrapped in a Kiro Power (`power/`). It is a
hand-written JSON-RPC 2.0 server with no SDK and no runtime dependency. Disk content is untrusted data: every name,
label and text it returns is sanitized and marked as untrusted.

Status: the workspace server (`.kiro/settings/mcp.json`) is verified by hand in Kiro. The Power in `power/` is verified
by hand in Kiro (2026-11-10): it installs in the Agent Plugins format, connects, opens an image and exhumes a file, and
it rejects the home folder as `workspace`. See "Manual check of the Power (owner)" for what was and was not checked.

### Tools
- `open_disk`: open a disk image inside the workspace and list its files with state (`alive`, `recovered`, `partial`,
  `lost`), size and date.
- `read_grave`: convert one file and return a preview (Markdown, CSV or plain text, or PNG dimensions). Takes `image`, `path`
  and an optional integer `id` from the `open_disk` listing, for when two entries share a path.
- `exhume`: convert one file and write the full result into the `exhumed/` folder of the workspace. It never
  overwrites an existing file.
- `explain_state`: return a fixed explanation of one state.

`exhumed/` is the only place the server writes. It is git-ignored.

### Platforms
macOS and Linux are supported. Windows is unsupported: Node has no `O_NOFOLLOW` there, so the no-symlink guarantee
cannot be given and the server refuses to start.

### Build and run
`power/server/exhume-mcp.mjs` is a committed build, refreshed with `npm run build:mcp`. Running that command is a
manual step for you. You can start the server by hand with:

```bash
node power/server/exhume-mcp.mjs [--root <dir>]
```

Without `--root` the server uses its working directory as the workspace root. It reads one JSON-RPC message per line
on standard input.

### Install in Kiro
1. Open the repository folder in Kiro as the workspace. Kiro reads the committed `.kiro/settings/mcp.json`, which has
   a single `exhume` entry:
   ```json
   { "mcpServers": { "exhume": { "command": "node", "args": ["power/server/exhume-mcp.mjs"] } } }
   ```
2. Check that the MCP Servers list shows `exhume` with its 4 tools. On a fresh clone it loads when the folder opens.
   If you added the file while the window was already open, run "Developer: Reload Window" from the command palette.
3. Check that the Kiro setting "Kiro Agent: Configure MCP" is Enabled (it is by default).

Kiro starts the server with the workspace root as its working directory, so `--root` is not needed. It is only an
option for when a client starts the server somewhere else: image calls then fail closed with `PATH_REJECTED` and
expose nothing, and you can append `"--root", "<absolute workspace path>"` to the `args` array of the `exhume` entry.

4. Agent Plugins format (a `plugin.json` with `$schema` `https://agent-plugins.org/schemas/1.0.0/plugin.schema.json`,
   tried on a scratch copy only): Kiro copies the whole folder including `server/`, expands `${PLUGIN_ROOT}` in `args`

confinement runs inside it. The result was checked by hand on 2026-11-10 (next section).

### Accepted residual risks
Path checks confine image reads to the workspace (no `..` escape, no symlinks, regular files only, size cap). These
risks are accepted and not hidden:
- In workspace mode the agent, not the user, chooses the confinement root. The root is visible in the chat's record
  of each tool call, and in the approval prompt when Kiro asks for one (with Autopilot on it may not ask). The server rejects the filesystem root, the user's home folder and every folder above it, but it
  accepts any other existing directory the agent names. That includes a parent of the folder the user opened when that
  parent lies below the home folder, and any directory outside the home folder, for example `/tmp` or `/Volumes/x`.
  Inside the chosen folder the image checks and the `exhumed/` write rules still apply.
- Node has no resolve-beneath open (`openat2` with `RESOLVE_BENEATH`). A local process that can already write inside
  the workspace could, in a window of microseconds, swap a directory for a symlink and back between the checks and the
  open. The server re-verifies the path and the file identity after opening, which narrows the window but cannot close
  it.
- A hard link inside the workspace to a file elsewhere on the same file system cannot be detected, so such a link is
  read as an ordinary file.
